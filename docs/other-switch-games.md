# 其他 Switch 游戏：macOS Sequoia 原生适配与打包流程

目标机器：M1 Pro、16GB 内存、macOS Sequoia 15。本文用于下次处理**不同的 Switch 游戏**，不固定游戏名称、标题 ID 或版本。

交付约定：代理完成源码适配、构建、数据完整性及签名校验，交付 App、构建说明和日志位置。**最终成品的启动、画面、声音、手柄、存档与性能测试由用户自行进行；不要自动运行游戏、预热 GPU 或操作成品。**

## 1. 先判断目标游戏需要多少适配

当前本地社区 fork 的 `games/` 下只有 `totk`。本次成功证明的是《王国之泪》1.2.1 在这台机器上的适配流程，不能据此保证任意 Switch 游戏都能直接生成可用 App。

每次开始新游戏，先检查该游戏的官方项目或社区移植目录、README、构建入口和固定提交：

| 实际情况 | 下一步 |
|---|---|
| 已有目标游戏、目标版本的 macOS 15 / Metal 3 移植 | 按该端口的构建流程校验输入并打包 |
| 已有目标游戏移植，但要求 macOS 26 / Metal 4 | 保留目标游戏的运行时和补丁，单独评估移植 Metal 3 后端及较旧系统 API 的工作量 |
| 已有目标游戏移植，但版本不同 | 分析代码与数据差异，为目标版本建立地址映射、指令保护和独立校验清单 |
| 尚无目标游戏移植 | 先做该游戏的原生移植可行性分析：代码重写、系统服务、图形、着色器、音视频等；仅解包和更换图标不能完成移植 |

优先使用目标游戏已有的端口。不要把游戏文件直接交给本次 `build_totk121.py`：该脚本和底层解析器仍固定了 TOTK 的标题、版本及布局。也不要套用另一个游戏的地址、模块哈希或数据结构。

## 2. 为每个新游戏收集输入

- **准确游戏名、地区、标题 ID、希望使用的版本。** 文件名只是线索，版本和身份还要通过包内容、元数据、模块哈希确认。
- **本体文件路径。** 格式由目标端口决定；确认是否接受 XCI、NSP、压缩格式，是否需要先解压。
- **独立更新包路径及版本。** 明确端口是否支持合并包、目标累计更新或其他包装方式。
- **本地 `prod.keys` 路径。** 检查需要的密钥代际和通用票据是否齐全；不输出密钥值。
- **固件或已提取字体路径（游戏需要时）。** 不能把“这个游戏不需要字体”或“必须提供整套固件”当成所有游戏的统一规则。
- **DLC、模组和存档（如确实需要）。** 逐项确认端口与版本支持；不能默认把上次塞尔达的限制套到别的游戏。
- **输出位置及磁盘余量。** 根据新游戏大小和构建步骤估算，不把上次约 17GB 数据或 60GB 余量当成统一标准。

这些输入可填写在同目录的 `其他Switch游戏打包需求模板.md` 中。

## 3. 保存源码、版本与工作目录

给每个游戏建立独立的源码目录、工作缓存和输出 App。不要复用另一款游戏的提取结果、改写模块、运行时表或着色器缓存。

建议结构：

```text
项目工作区/
  sources/<游戏代号>/        固定版本源码与适配代码
  work/<游戏代号>/<版本>/    提取数据、临时文件、编译与着色器缓存
  outputs/<游戏名称>.app     交付成品
  outputs/<游戏代号>-构建记录.md
```

遵守各源码项目自己的目录规则，生成物放在源码目录之外。缓存和 App 尽量位于同一个 APFS 卷；实际节省空间还取决于打包程序是否使用 APFS 克隆。

记录仓库 URL、分支、基础提交、引入补丁的来源，以及最终本地修改。保存只含源码的快照或可恢复补丁，避免以后只知道“用某个最新分支”。

## 4. 分开处理“游戏版本适配”和“Sequoia 适配”

### 游戏本身

核对目标游戏的 ExeFS 模块、ARM64 重写规则、入口和重定位、SDK 导入、系统服务、文件系统、内存、线程、输入、音视频、图形及着色器实现。

版本变化时，基于实际代码匹配补丁位置，检查原始指令并保留保护条件。单独建立该游戏该版本的模块、改写结果与最终数据校验清单。不能只更改版本字符串，也不能因构建失败就把期望哈希替换为未知输入的哈希。

### macOS 15 / Metal 3

检查目标端口实际用到的 Metal 4 和其他 macOS 26 API，逐项提供旧接口实现、受保护的可选功能或明确的兼容限制。某个游戏的 Metal 3 后端只能在接口和行为兼容时复用。

将启动器、游戏运行时和必要辅助程序的部署目标设到 macOS 15 支持范围。检查所有随包可执行文件的最低系统版本和依赖；仅更改 `Info.plist` 的最低版本字段不足以完成适配。

`TOTK_M3=1` 是本次塞尔达端口的开关，其他端口可能使用完全不同的参数或根本没有现成开关，应按实际构建配置处理。

## 5. 按目标端口构建

1. **环境检查：** 核对系统、架构、Xcode/SDK、目标端口要求的 Python或其他运行时、音视频库和构建工具。只安装缺少的依赖。
2. **输入检查：** 确认标题、版本、解密、票据和文件完整性。必要时安全提取固件或字体。
3. **代码处理：** 提取所需模块，执行该端口的 ARM64 重写和补丁，生成对应版本运行时表。
4. **数据处理：** 合并所需更新并验证文件系统完整性及最终数据身份。
5. **图形资源：** 按该游戏的着色器转换链生成资源与启动缓存。数量和清单以该游戏为准，不能要求其他游戏也恰好有 8,286 个。
6. **编译打包：** 编译兼容 Sequoia 的程序，装配只含所选游戏和版本的 App，核对资源路径、图标和版本信息。
7. **签名交付：** 执行本地签名和静态完整性检查。对自己刚生成且已校验的 App，处理可能继承的隔离属性；不更改系统全局安全设置。
8. **停止在交付阶段：** 禁用构建脚本隐含的启动测试，记录如何手动打开、如何开启日志及已知限制，交给用户测试。

每一步保留进度和日志，重跑优先复用本游戏本版本已校验的缓存。网络下载或大文件校验没有持续输出时，先看进程及日志，不启动重复构建。

## 6. 这次经验中可以复用的处理方法

| 经验 | 在其他游戏上如何使用 |
|---|---|
| 先检查端口和真实输入再构建 | 通用方法；解析器必须识别新游戏的身份和布局 |
| 原密钥文件有无关格式错误 | 根据所用工具实际需要的字段建立私有临时副本，保留原文件，退出后删除；字段集合不能盲目照搬 |
| 固件字体版本不同 | 验证来源、格式与完整性，确认新游戏对字体的要求，再增加可追溯支持；不能仅放宽检查 |
| 本体和更新的代码元数据不同 | 根据目标更新的完整 ExeFS 与数据合并方式决定哪些文件实际被使用，不普遍忽略 NPDM 或其他检查 |
| 新生成 App 被隔离标记阻止 | 从系统日志、签名和扩展属性定位；已确认的本地构建可处理自身隔离属性，其他崩溃另查原因 |
| 大型资源和缓存很耗磁盘 | 分离源码、缓存与输出，按实际游戏估算空间并利用 APFS 克隆 |
| 启动成功不等于游戏兼容 | 报告应区分构建与静态校验结果、用户反馈和未验证事项 |

## 7. 交付与用户反馈

每款游戏最终交付：

- 成品 App、准确游戏版本、最低系统版本和图形后端。
- 固定源码与适配补丁或快照。
- 可复用的**该游戏专用**构建入口、参数示例和依赖清单。
- 构建与静态校验结果、日志路径和已知限制。
- 可清理的中间目录及需要保留的缓存说明；未经要求不删除用户原文件、存档或已有成品。

用户自行测试后，优先提供打不开时的提示、崩溃报告或相关日志末尾，以及出现问题的场景。再依据这些反馈修复；不提前声称已通过画面、帧率或长期稳定性测试。

## 塞尔达案例的位置

同目录的 `Sequoia打包流程.md`、`build_totk121.py`、源码快照和适配补丁，均是本次 **TOTK 1.2.1 专用案例**。它们提供可参考的工作方法与部分实现，不是任意 Switch 游戏通用的转换器。
